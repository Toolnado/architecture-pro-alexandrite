# Планирование: анализ, идентификация проблем и поиск решений

## 1. Идентификация проблем

### 1.1 Текущие (уже проявляются в продакшне)

**P1 — Очередь RabbitMQ является узким местом и источником потерь заказов**

MES и CRM общаются через одну очередь, в которой смешаны принципиально разные по природе сообщения: задачи на расчёт стоимости (которые занимают от 2 до 30 минут) и события о смене статусов заказов. Когда внешний API открыл шлюз для партнёров, объём задач на расчёт резко вырос. Очередь начала "вставать", и события о статусах (MANUFACTURING_APPROVED, SHIPPED и т.д.) стали доставляться с большой задержкой или не доставляться вовсе — их просто вытесняют из буфера или consumer не успевает их обрабатывать. Отсюда и симптом: заказы числятся "в работе несколько месяцев", хотя производство справляется.

**P2 — Отсутствие observability**

О проблемах узнаём из жалоб клиентов и менеджеров, а не из метрик и алертов. Нет понимания: сколько сообщений сейчас в очереди, какой latency у запросов, где конкретно застревает заказ. Без мониторинга любая диагностика — это "лечим вслепую".

**P3 — Медленная загрузка дашборда MES**

Единственная БД MES обслуживает одновременно и записи от производственных операций (изменения статусов, новые заказы), и тяжёлые read-запросы от дашборда. Фильтрация по статусам и пагинация не помогли — проблема, скорее всего, в отсутствии составных индексов по `(status, created_at)` и в конкуренции между read и write на одном инстансе.

**P4 — Нет rate limiting на внешнем API**

После открытия API компанию "завалило заказами". Это означает, что партнёры могут слать запросы с любой скоростью, без ограничений. Система не защищена от случайного или намеренного flood'а — и именно это, в сочетании с P1, вызвало деградацию всей системы.

**P5 — Медленный цикл доставки изменений (CI/CD)**

Деплой в release и prod — ручной. QA-инженер один, тестирует руками, при нахождении high/highest багов блокирует релиз. Задержки выросли с одного месяца до нескольких. Это означает, что даже когда мы найдём и починим критические баги (P1, P3), до пользователей исправление будет идти долго.

---

### 1.2 Потенциальные (риски при продолжении роста)

**P6 — Единая точка отказа для каждого приложения**

Каждое из трёх приложений работает в одном инстансе EC2. Падение одного инстанса — полный простой соответствующего сервиса. При росте нагрузки вертикальное масштабирование (upgrade EC2) имеет предел и ненулевой downtime.

**P7 — БД без репликации**

Одна БД работает на чтение и запись. Нет резервной копии в hot-standby. Сбой БД = потеря данных или длительный простой.

**P8 — Хранилище 3D-файлов может стать узким местом**

Файлы загружаются пользователями и читаются MES при расчёте. При росте числа заказов конкуренция за хранилище увеличивается. Если это не managed object storage (S3-совместимый), а, например, сетевой диск, это проблема.

**P9 — Нет нотификаций клиентов о статусах заказа**

Клиенты узнают о задержках только через менеджеров. Это создаёт нагрузку на людей и ухудшает опыт пользователя. При дальнейшем росте менеджеры не справятся.

**P10 — Расчёт стоимости — синхронная операция с неограниченным временем**

Партнёры через API получают ответ... когда? Если MES считает 30 минут — как это обрабатывается на стороне клиента? Вероятно, долгий HTTP timeout или polling без чёткого контракта. Это источник ненадёжности интеграции.

## 2. Инициативы

| # | Инициатива | Что решает |
|---|-----------|-----------|
| I1 | Внедрить observability: метрики, трейсинг, алертинг | P2 |
| I2 | Разделить очереди RabbitMQ по типам сообщений | P1 |
| I3 | Перевести расчёт стоимости на асинхронную модель (requestId + callback/polling) | P1, P10 |
| I4 | Добавить rate limiting и throttling на внешний API | P4 |
| I5 | Добавить read replica для БД MES + индексы по статусам/датам | P3 |

| I7 | Настроить горизонтальное масштабирование (ALB + несколько инстансов) | P6 |
| I8 | Настроить репликацию и резервное копирование БД | P7 |

## 3. Приоритизация инициатив

### Логика расстановки приоритетов

Приоритизирую по принципу: сначала — что прямо сейчас теряет деньги и клиентов, потом — что не даст скатиться в ту же яму снова, затем — что нужно для уверенного роста.

**Уровень 1 — Горящий дом (делать немедленно):**

1. **I1 — Observability.** Без неё всё остальное делаем вслепую. Нельзя починить то, что не видишь. Минимальный набор: метрики глубины очереди RabbitMQ, latency API, количество заказов по статусам, error rate. Это первое, что ставим — за один спринт.

2. **I2 — Разделение очередей RabbitMQ.** Это, судя по всему, корневая причина потерянных заказов. Расчёт стоимости (долгая операция) блокирует статусные события (короткие). Разделяем на отдельные exchanges/queues с разными consumer-группами. Можно сделать быстро, не трогая логику — только конфигурация очереди и небольшие правки в коде.

3. **I4 — Rate limiting на API.** Пока нет ограничений, партнёры могут случайно (или намеренно) положить систему повторно. Добавляем throttling по API key — это час работы на уровне gateway или middleware.

**Уровень 2 — Убрать следующий пожар (делать в этом квартале):**

4. **I3 — Асинхронный расчёт стоимости.** Это архитектурное изменение, которое делает систему устойчивой к пиковым нагрузкам. MES принимает задачу → возвращает `requestId` → присылает результат через webhook или отдаёт по polling-эндпоинту. Это снимает нагрузку с очереди и делает интеграцию с партнёрами предсказуемой.

5. **I6 → I5 — Оптимизация дашборда MES, затем read replica.** Сначала проверяем query plan и добавляем индексы — это быстро и бесплатно. Если не помогает, добавляем read replica. Это разгрузит основную БД и сделает дашборд быстрым.

6. **I9 — Автоматизация тестирования.** QA-инженер уже делал прототипы автотестов — поддержать его. Покрыть критические E2E-сценарии (создание заказа, расчёт стоимости, смена статуса). Это ускорит цикл релизов и снизит риск блокировок.

**Уровень 3 — Рост и надёжность (следующие 3–6 месяцев):**

7. I7 — Горизонтальное масштабирование
8. I8 — Репликация БД
9. I10 — Нотификации клиентам
10. I11 — Аудит file storage

## 4. Целевая архитектура через полгода

Через полгода вижу систему, которая перестала быть реактивной ("тушим пожары") и стала проактивной.

**Observability.** Есть дашборды с ключевыми метриками: глубина очереди, latency расчёта, количество заказов по статусам, error rate. Алерты уходят в мессенджер дежурному, а не клиентам на почту.

**Обработка заказов.** Очередь RabbitMQ разделена: отдельный exchange для задач расчёта стоимости, отдельный — для статусных событий. Расчёт стоимости — асинхронный: MES принимает задачу, возвращает `requestId`, результат доступен через polling или webhook. Это снимает bottleneck и делает API предсказуемым для партнёров.

**API.** Внешний API защищён rate limiting'ом по API key. Партнёры получают понятный контракт: как отправить заказ, как узнать стоимость, как отслеживать статус.

**Производительность.** БД MES имеет read replica. Дашборд операторов читает из реплики, запись идёт в мастер. Индексы по `(status, created_at)` добавлены. Дашборд загружается быстро.

**Доставка изменений.** Критические E2E-сценарии покрыты автотестами — QA не является единственным барьером перед продакшном. Цикл релиза сократился.

**Инфраструктура.** Приложения работают за load balancer'ами с возможностью добавить инстанс без downtime. БД имеют репликацию и регулярные бэкапы.

Архитектура всё ещё монолитная по компонентам — это нормально для текущей команды. Мы не делаем микросервисы ради микросервисов: команда маленькая, а накладные расходы на координацию между сервисами нас убьют быстрее, чем монолит.

## 5. Три приоритетных инициативы на полгода

Если бы у меня был выбор только трёх инициатив, я бы выбрал:

### 1. I1 + I2: Observability и разделение очередей (связанные, делаем вместе)

Это корень всех текущих болей. Потеря крупных контрактов, жалобы клиентов, застревающие заказы — всё это либо вызвано перегрузкой очереди, либо мы просто не видим, что происходит. Разделение очередей устранит конкуренцию между долгими задачами (расчёт стоимости) и быстрыми событиями (статусы). Observability даст нам возможность убедиться в этом и быстро реагировать в будущем. Без мониторинга мы не поймём, помогло ли разделение очередей.

Эффект: заказы перестают теряться, операторы видят актуальные статусы, бизнес перестаёт терять контракты.

### 2. I3: Асинхронный расчёт стоимости

Это архитектурное решение, которое снимает системное ограничение. Пока расчёт стоимости — это синхронная операция в очереди, которая может занять 30 минут, система будет деградировать при любом росте нагрузки. Переход на асинхронную модель (requestId + callback) делает систему устойчивой к пиковым нагрузкам и даёт партнёрам предсказуемый интерфейс. Это также позволит в будущем горизонтально масштабировать воркеры расчёта независимо от остального стека.

Эффект: система не ложится при росте числа партнёров, контракты с B2B не теряются из-за таймаутов.

### 3. I9: Автоматизация тестирования (покрытие критических E2E-сценариев)

Даже если мы всё починим архитектурно, медленный цикл релиза будет тормозить нас при каждом следующем изменении. QA-инженер хочет заниматься автоматизацией и уже делал прототипы — нужно дать ему на это время и ресурсы. Достаточно покрыть 5–7 ключевых сценариев (создание заказа, расчёт стоимости, смена статуса, отправка заказа), чтобы снять блокировку релизов из-за регрессий. Это инвестиция, которая окупается на каждом последующем спринте.

Эффект: циклы релиза ускоряются, исправления и новые фичи быстрее попадают к пользователям.
