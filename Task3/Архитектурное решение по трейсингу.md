# Архитектурное решение по трейсингу

## Системы и точки, покрываемые трейсингом

На диаграмме C4 выделены три сервиса, через которые проходит жизненный цикл заказа и где он может «застрять» или потеряться:

- **Shop API** (Spring Boot) — создаёт заказ, принимает 3D-файл, передаёт заказ в CRM
- **CRM API** (Spring Boot) — меняет статусы заказа, публикует и потребляет события из RabbitMQ
- **MES API** (C#) — рассчитывает стоимость, принимает запросы от внешних партнёров через публичный API, управляет производственными статусами

RabbitMQ (Messages Queue) является точкой стыковки между CRM и MES — именно здесь теряются сообщения. Трейсинг охватывает оба конца: публикацию сообщения в очередь и его потребление на другой стороне.

### Места, где заказ может «сломаться»

| # | Место | Описание риска |
|---|-------|----------------|
| 1 | Shop API → CRM API | Вызов после SUBMITTED может упасть или зависнуть, заказ не попадёт в CRM |
| 2 | Shop API → 3d files storage | Загрузка файла упала — заказ не перейдёт в FILE_UPLOADED |
| 3 | CRM API → RabbitMQ (publish) | Сообщение не опубликовано — MES не получит задачу на расчёт |
| 4 | RabbitMQ → MES API (consume) | Consumer перегружен или упал — очередь растёт, заказы ждут |
| 5 | MES API (расчёт стоимости) | Расчёт занимает до 30 мин — нет span'а с длительностью → нет SLO |
| 6 | MES API → RabbitMQ (publish PRICE_CALCULATED) | Событие не отправлено — CRM никогда не узнает о результате |
| 7 | RabbitMQ → CRM API (consume PRICE_CALCULATED) | Сообщение не доставлено или отклонено — заказ застрял в SUBMITTED |
| 8 | CRM API → RabbitMQ (publish MANUFACTURING_APPROVED) | Менеджер подтвердил, но MES не получил — производство не начнётся |
| 9 | MES API (публичный B2B API) | Партнёр отправил запрос — непонятно, был ли он обработан |

## Список данных, которые должны попадать в трейсинг

### Обязательные атрибуты каждого спана

| Атрибут | Значение |
|---------|---------|
| `order_id` | ID заказа — главный ключ корреляции, присваивается при создании заказа |
| `order_status` | Статус заказа на момент операции (до и после, если меняется) |
| `order_source` | `b2c` / `b2b` — откуда пришёл заказ |
| `service.name` | Имя сервиса (`shop-api`, `crm-api`, `mes-api`) |
| `service.version` | Версия деплоя |
| `environment` | `prod` / `release` / `dev` |

### HTTP-спаны (входящие и исходящие запросы)

| Атрибут | Пример |
|---------|--------|
| `http.method` | `POST` |
| `http.url` | `/api/orders` |
| `http.status_code` | `200`, `500` |
| `http.request_content_length` | для MES API (3D-файлы большие) |

### RabbitMQ-спаны (публикация и потребление)

| Атрибут | Пример |
|---------|--------|
| `messaging.system` | `rabbitmq` |
| `messaging.destination` | имя exchange или очереди |
| `messaging.operation` | `publish` / `receive` |
| `messaging.message_id` | ID сообщения для корреляции |

### База данных (автоматически через OTel)

| Атрибут | Пример |
|---------|--------|
| `db.system` | `postgresql` |
| `db.operation` | `SELECT` / `INSERT` |
| `db.statement` | запрос (без значений параметров — PII могут быть в значениях) |

### События внутри спанов (span events)

| Событие | Когда |
|---------|-------|
| `order.status_changed` | При каждой смене статуса заказа |
| `price_calculation.started` | Начало расчёта стоимости в MES |
| `price_calculation.completed` | Завершение расчёта |
| `validation.failed` | Ошибка валидации входных данных |

### Что **не должно** попадать в трейсинг

- ФИО клиентов, адреса доставки, номера телефонов
- Платёжная информация
- Содержимое 3D-моделей
- Пароли и токены авторизации

## Мотивация

Сейчас, когда заказ не приходит клиенту, команда узнаёт об этом через цепочку: клиент → менеджер → продакт → разработчик → «давайте посмотрим логи каждого сервиса по очереди». Это занимает часы и требует участия нескольких людей.

Трейсинг — это инструмент, который позволяет увидеть полный путь заказа через систему в одном интерфейсе. Зайти по `order_id` в Jaeger и за секунды понять: на каком шаге заказ остановился, какой сервис ответил с ошибкой, сколько времени ушло на расчёт стоимости, дошло ли сообщение до MES.

### Технические и бизнес-метрики, на которые повлияет внедрение

| Метрика | До | После |
|---------|-----|-------|
| **Среднее время диагностики инцидента** | Часы (ручной анализ логов нескольких сервисов) | Минуты (поиск по order_id в Jaeger) |
| **Доля заказов с неизвестным местом потери** | ~100% потерянных заказов — без чёткого ответа, где именно | <5% — остаток только там, где трейсинг не покрывает (внешние системы) |
| **MTTR (Mean Time To Resolve)** | Нет baseline, очевидно высокий | Ожидаемое снижение ×3–5 за счёт быстрой локализации |
| **SLO на расчёт стоимости** | Не определён, неизмерим | После трейсинга можно определить p95 latency расчёта и ввести SLO |
| **Потери контрактов из-за необъяснённых задержек** | Несколько крупных контрактов потеряно | Каждый инцидент объясним с деталями — это восстанавливает доверие партнёров |

## Предлагаемое решение

### Технологический стек

**OpenTelemetry (OTel)** — стандарт инструментирования. Используем вместо проприетарных SDK потому, что он vendor-neutral: если в будущем захотим поменять Jaeger на Grafana Tempo или Datadog, не придётся переписывать код сервисов.

**Jaeger All-in-One** — бэкенд для хранения и поиска трейсов. Простое развёртывание на одном EC2-инстансе (или контейнере), хорошая UI для поиска по `order_id` и визуализации waterfall-диаграмм.

**OTel Collector** — промежуточный компонент, который принимает спаны от сервисов, батчит их и отправляет в Jaeger. Он же умеет трансформировать, фильтровать и в будущем отправлять данные в несколько систем одновременно. Без коллектора каждый сервис писал бы напрямую в Jaeger — это tight coupling.

### Инструментирование сервисов

**Shop API и CRM API (Spring Boot Java):**
Добавляем зависимость `opentelemetry-spring-boot-starter`. Автоинструментирование покрывает:
- Входящие и исходящие HTTP-запросы
- JDBC-запросы к базам данных
- Исходящие вызовы через RestTemplate/WebClient

Для RabbitMQ — зависимость `opentelemetry-instrumentation-rabbitmq`. Она автоматически пробрасывает контекст через заголовки сообщений (W3C Trace Context).

Кастомные атрибуты (`order_id`, `order_status`, `order_source`) добавляем вручную через `Span.current().setAttribute(...)` в местах смены статуса.

**MES API (C# ASP.NET Core):**
Добавляем NuGet-пакеты `OpenTelemetry.Extensions.Hosting` и `OpenTelemetry.Instrumentation.AspNetCore`. Автоинструментирование покрывает HTTP и ADO.NET. Для RabbitMQ — `OpenTelemetry.Instrumentation.RabbitMQ`. Для кастомных спанов (время расчёта стоимости) — `ActivitySource` API.

### Конфигурация OTel Collector

OTel Collector разворачивается как отдельный EC2-инстанс (или Docker-контейнер). Настраивается через YAML:

- **Receivers:** `otlp` (gRPC на порту 4317, HTTP на 4318)
- **Processors:** `batch` (для снижения количества запросов к Jaeger), `memory_limiter` (защита от OOM)
- **Exporters:** `jaeger` (gRPC)
- **Sampling:** на старте — `always_on` (100% трейсов), после стабилизации переходим на head-based sampling с коэффициентом 10–20% для типовых запросов, 100% для ошибочных

### Бонус: Автоматический мониторинг прохождения заказов и алертинг

Трейсинг сам по себе — реактивный инструмент: нужно открыть Jaeger и поискать. Чтобы команда узнавала о проблемах **до** жалобы клиента, добавляем автоматический анализ span-метрик.

#### Как это работает

OTel Collector имеет встроенный `spanmetrics` коннектор, который автоматически генерирует Prometheus-метрики из потока спанов:
- `traces_spanmetrics_calls_total{service, operation, status}` — количество вызовов по статусу
- `traces_spanmetrics_duration_milliseconds{service, operation}` — гистограмма времени выполнения

Эти метрики экспортируются в **VictoriaMetrics** (time-series БД). **Grafana** читает метрики из VictoriaMetrics и трейсы из Jaeger. Для каждого алерта в Grafana можно одним кликом перейти к соответствующему трейсу в Jaeger — это называется exemplars.

**Alertmanager** получает сработавшие алерты от Grafana и маршрутизирует уведомления дежурному инженеру в Telegram.

#### Правила алертинга на основе трейсов

| Правило | Условие | Severity | Действие |
|---------|---------|----------|----------|
| Заказ завис в статусе SUBMITTED | `avg(order_age_by_status{status="SUBMITTED"}) > 15m` | critical | Telegram дежурному, заводится тикет |
| Ошибки в MES API (расчёт стоимости) | `rate(traces_spanmetrics_calls_total{service="mes-api", status="ERROR"}[5m]) / rate(traces_spanmetrics_calls_total{service="mes-api"}[5m]) > 0.05` | critical | Немедленный алерт — партнёры получают ошибки |
| Деградация latency Shop API | `histogram_quantile(0.95, traces_spanmetrics_duration_milliseconds{service="shop-api"}) > 3000` | warning | Алерт тимлиду |
| Расчёт стоимости занимает >25 мин | `histogram_quantile(0.99, traces_spanmetrics_duration_milliseconds{service="mes-api", operation="calculate_price"}) > 1500000` | warning | Алерт — возможно, зависший воркер |
| Сообщение не дошло от CRM до MES (разрыв трейса) | Специальный span event `messaging.receive` не появился через 5 мин после `messaging.publish` | critical | Немедленный алерт — потеря событий |

## Компромиссы

### 1. MES API — высокая стоимость инструментирования

MES куплен с исходным кодом, но написан на C#. В команде один C#-разработчик (и тимлид с опытом C#). Автоинструментирование OpenTelemetry для .NET покрывает HTTP и базу данных, но кастомные спаны (время расчёта стоимости, события смены производственного статуса) нужно добавлять вручную. Это требует времени и отвлекает от других задач. Риск: первая версия трейсинга для MES будет неполной — это лучше, чем откладывать всё до полного покрытия.

### 2. Трейсинг не покрывает внешние системы

Заказ закрывается (статус CLOSED) после сообщения от транспортной компании. Это внешняя система — мы видим только момент получения её сообщения, но не можем трассировать то, что происходит на её стороне. Аналогично с партнёрами-пользователями API: мы видим, что запрос пришёл к нам и обработан, но не знаем, что происходит в их системах.

### 3. Семплирование и стоимость хранения

Расчёт стоимости занимает до 30 минут. При 100% семплировании и росте числа заказов (+100 в месяц) объём трейсов будет расти быстро. Jaeger с дефолтным хранилищем (Badger) хранит трейсы 7 дней — при высокой нагрузке этого может не хватить для расследования инцидентов прошлой недели. Решение: переход на Jaeger + Elasticsearch backend или head-based sampling (не трассировать успешные запросы полностью, только при ошибках и медленных ответах).

### 4. Контекст через RabbitMQ требует синхронного деплоя

Пропагация trace context через заголовки RabbitMQ работает только когда оба конца (публикация и потребление) инструментированы. Если задеплоить CRM API с OTel раньше, чем MES API — трейсы будут обрываться на RabbitMQ. Нужно координировать деплой или принять, что в переходный период будут «битые» трейсы.

### 5. Производительность при 100% семплировании

OTel добавляет ~1–3% overhead на latency. Для расчёта стоимости (2–30 мин) это незначимо. Для Shop API с быстрыми (<100ms) запросами — 1–3ms дополнительной latency допустимо. Если нет — переходим на 10–20% семплирование быстрее.

## Безопасность

### Доступ к Jaeger UI

- **Jaeger UI** доступен только из внутренней сети (VPC). Прямой доступ из интернета закрыт через Security Group на уровне Yandex Cloud.
- Дополнительно: NGINX reverse proxy перед Jaeger с HTTP Basic Auth или интеграция с корпоративным SSO (Keycloak или Yandex 360 OAuth), если он используется.
- **Роли доступа:** чтение трейсов — роль "Support" и "Engineering"; настройка — только DevOps и тимлид.

### OTel Collector endpoint

- Порты 4317 (gRPC) и 4318 (HTTP) слушают только на `0.0.0.0` внутри VPC. Снаружи закрыты. Сервисы подключаются по внутреннему DNS-имени коллектора.
- TLS между сервисами и коллектором: настраивается через `tls` секцию в конфиге OTel Collector. На первом этапе допустимо работать без TLS, так как трафик идёт внутри VPC.

### Данные в спанах

- Строгое правило: в атрибуты спанов не попадают PII-данные (ФИО, адреса, телефоны, email клиентов). Только технические идентификаторы (`order_id`, `user_id`).
- Перед деплоем — code review на предмет случайного логирования чувствительных данных в спаны.
- OTel Collector может быть настроен как дополнительный слой защиты: процессор `transform` с правилами удаления или маскирования атрибутов по маске перед отправкой в Jaeger.

### Аудит доступа к Jaeger

- Включить access log на уровне NGINX-прокси перед Jaeger: кто и когда смотрел трейсы. Это важно, поскольку трейсы содержат информацию о бизнес-операциях (какие заказы, от каких партнёров).
