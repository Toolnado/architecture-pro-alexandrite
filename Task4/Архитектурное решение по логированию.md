# Архитектурное решение по логированию

## Системы, требующие сбора логов

На C4-диаграмме тремя источниками логов являются три серверных компонента: **Shop API**, **CRM API** и **MES API**. Именно через них проходит полный жизненный цикл заказа, и именно в этих точках заказ может «застрять» или потеряться.

Обновлённая диаграмма с компонентами логирования (оранжевый цвет):
[**c4-logging.drawio**](diagrams/c4-logging.drawio)

> Для просмотра откройте файл на [app.diagrams.net](https://app.diagrams.net) (File → Open from → Device).

Frontend-приложения (Internet Shop, CRM, MES) — браузерные SPA. Логи из браузера (JavaScript-ошибки) тоже имеют ценность, но это отдельная задача (browser error tracking через Sentry или аналог). В текущей итерации не включаем.

## Какие логи собирать

### Уровень INFO — список обязательных событий

Все поля логов указаны в контексте структурированного JSON-лога. Поля `trace_id` и `span_id` берутся из OTel-контекста (связь с трейсингом из Task 3).

#### Shop API

| Событие | Поля |
|---------|------|
| Заказ создан (INITIATED) | `order_id`, `user_id`, `order_source=b2c`, `timestamp` |
| Файл 3D-модели загружен (FILE_UPLOADED) | `order_id`, `user_id`, `file_id`, `file_size_bytes`, `timestamp` |
| Заказ отправлен пользователем (SUBMITTED) | `order_id`, `user_id`, `timestamp` |
| HTTP-запрос завершён | `method`, `path`, `status_code`, `duration_ms`, `user_id` |
| Вызов CRM API завершён | `order_id`, `crm_endpoint`, `status_code`, `duration_ms` |
| Загрузка файла в S3 завершена | `order_id`, `file_id`, `duration_ms` |

#### CRM API

| Событие | Поля |
|---------|------|
| Заказ получен от Shop API | `order_id`, `user_id`, `timestamp` |
| Статус заказа изменён | `order_id`, `old_status`, `new_status`, `actor_id`, `actor_type` (seller/system), `timestamp` |
| Сообщение опубликовано в RabbitMQ | `order_id`, `exchange`, `routing_key`, `message_type`, `timestamp` |
| Сообщение получено из RabbitMQ | `order_id`, `queue_name`, `message_type`, `processing_started_at` |
| Сообщение обработано из RabbitMQ | `order_id`, `queue_name`, `message_type`, `duration_ms` |
| Заказ подтверждён к производству (MANUFACTURING_APPROVED) | `order_id`, `seller_id`, `timestamp` |
| Заказ закрыт (CLOSED) | `order_id`, `close_reason` (transport/manual), `timestamp` |
| HTTP-запрос завершён | `method`, `path`, `status_code`, `duration_ms`, `seller_id` |

#### MES API

| Событие | Поля |
|---------|------|
| Запрос расчёта стоимости получен | `order_id`, `request_type` (b2c/b2b), `partner_id` (для b2b), `timestamp` |
| Расчёт стоимости начат | `order_id`, `model_file_id`, `timestamp` |
| Расчёт стоимости завершён | `order_id`, `price_amount`, `price_currency`, `duration_ms`, `timestamp` |
| Статус производства изменён | `order_id`, `old_status`, `new_status`, `operator_id`, `timestamp` |
| Оператор взял заказ в работу (MANUFACTURING_STARTED) | `order_id`, `operator_id`, `timestamp` |
| Заказ изготовлен (MANUFACTURING_COMPLETED) | `order_id`, `operator_id`, `duration_ms` (от STARTED до COMPLETED) |
| Заказ отправлен (SHIPPED) | `order_id`, `tracking_number`, `carrier`, `timestamp` |
| Сообщение опубликовано / получено из RabbitMQ | `order_id`, `queue_name`, `message_type`, `timestamp` |
| HTTP-запрос завершён | `method`, `path`, `status_code`, `duration_ms`, `partner_id` (если b2b) |

### Другие уровни логирования

**DEBUG**
Используется только в dev и release окружениях, в prod отключён. Содержит: полные тела входящих/исходящих запросов (sanitized, без чувствительных данных), параметры SQL-запросов, внутренние состояния при сложных вычислениях. Включается временно по запросу при расследовании конкретного инцидента.

**WARN**
Фиксирует ситуации, которые не привели к ошибке, но требуют внимания:
- Превышение порогового времени ответа зависимости (например, расчёт стоимости занял >20 мин)
- Повторная попытка (retry) при временной недоступности зависимости
- Нестандартный код ответа от внешней системы (4xx от партнёра)
- Сообщение в очереди обрабатывается дольше ожидаемого
- Запрос с подозрительно высоким RPS от одного partner_id

**ERROR**
Фиксирует ситуации, когда операция не выполнена из-за ошибки. Обязательно включает: `error_type`, `error_message`, `stack_trace` (для Java/C# — сокращённый, без чувствительных фреймов), `order_id` если применимо, `trace_id` для корреляции с трейсом.

Примеры: недоступность базы данных, недоступность RabbitMQ, HTTP 5xx от зависимости, неожиданное исключение в бизнес-логике, ошибка публикации/потребления сообщения.

**FATAL**
Используется только при невозможности продолжить работу сервиса: нет подключения к БД при старте, некорректная конфигурация, критическая ошибка инициализации. После FATAL — процесс завершается и k8s/systemd его перезапускает.

## Мотивация

Сейчас диагностика каждого инцидента — это ручная работа: разработчик смотрит логи на каждом из трёх серверов по отдельности, пытается восстановить хронологию событий по частичным данным. На это уходят часы, а иногда и дни. Проблема усугубляется тем, что в системе нет единого идентификатора заказа, который бы связывал события в разных сервисах.

Структурированное централизованное логирование решает это: инженер открывает Grafana, вводит `order_id`, видит полную хронологию событий по всем сервисам в одном месте.

### Технические и бизнес-метрики, которые изменятся после внедрения

| Метрика | До | После |
|---------|-----|-------|
| **MTTR** (среднее время устранения инцидента) | ~4–8 часов (ручная диагностика по трём серверам) | ~30–60 минут (поиск по order_id в Grafana) |
| **Доля инцидентов без root cause** | Высокая: часть инцидентов закрывается без понятной причины | <10%: каждый ERROR-лог содержит достаточно контекста для root cause analysis |
| **Нагрузка на поддержку** | Каждая жалоба клиента требует участия разработчика | Тим саппорта может самостоятельно ответить клиенту, просмотрев логи без разработчика |
| **Время обнаружения аномалий** | Дни (от жалобы клиента до расследования) | Минуты (алерт на резкий рост ошибок или аномальный RPS) |
| **Видимость B2B партнёрских запросов** | Нулевая: нет никаких логов для партнёрских обращений | Полная: каждый запрос от партнёра логируется с `partner_id`, можно показывать отчёты по партнёрам |

## Приоритет внедрения: логирование и трейсинг

Команда не может одновременно покрыть все три сервиса. Приоритет определяется по принципу «максимальный бизнес-эффект минимальными ресурсами».

### 1-й приоритет: CRM API + MES API (вместе, один спринт)

Это обе стороны RabbitMQ-очереди — именно здесь заказы застревают и теряются. CRM API публикует события в очередь и потребляет ответы от MES; MES API потребляет задачи на расчёт и публикует результаты. Без логов с обеих сторон невозможно понять, где именно рвётся цепочка: до публикации в очередь, после публикации или на стороне потребителя.

Spring Boot (CRM API) инструментируется за несколько часов: добавить Logback + Logstash encoder + запись ключевых событий с MDC-контекстом. C# (MES API) — Serilog с JSON-форматтером. Это минимальные изменения с максимальным эффектом для текущей проблемы.

### 2-й приоритет: Shop API (следующий спринт)

Shop API понять проще: там нет асинхронного взаимодействия через очередь. Ошибки в Shop API чаще синхронные и заметнее. Инструментировать его важно, но не так срочно, как покрыть границу CRM↔MES.

### Frontend (низкий приоритет)

Логи из браузера (JavaScript-ошибки) дают ценность для UX, но не для расследования потерянных заказов. Откладываем на более поздний этап, когда будет внедрён Sentry или аналог.

## Предлагаемое решение

### Стек технологий

**Grafana Loki** — хранилище логов. Причины выбора:
- В инфраструктуре уже есть Grafana (Task 2/3). Loki — нативный datasource, настраивается за один вечер.
- Не индексирует содержимое логов (в отличие от Elasticsearch) — требует в 10–50 раз меньше дискового пространства.
- Достаточно мощный для текущей нагрузки: при +100 заказов/месяц объём логов не критический.
- Встроенная корреляция с трейсами: из лога можно перейти к трейсу по `trace_id` одним кликом.

**Promtail** — агент сбора логов. Запускается как systemd unit или sidecar на каждом EC2-инстансе. Читает stdout/stderr процесса, добавляет метки (`service`, `env`, `instance`) и отправляет в Loki.

**Logback + Logstash Encoder** (для Java Spring Boot сервисов) — библиотека для структурированного JSON-логирования. Добавляет `trace_id`/`span_id` из OTel MDC автоматически.

**Serilog + Serilog.Formatting.Compact** (для C# MES API) — аналог для .NET. Поддерживает структурированный JSON-вывод в stdout.

### Формат лога

```json
{
  "timestamp": "2024-11-15T14:32:01.456Z",
  "level": "INFO",
  "service": "crm-api",
  "environment": "prod",
  "trace_id": "4f3a9b2c1d0e5f6a",
  "span_id": "7b8c9d0e1f2a3b4c",
  "event": "order.status.changed",
  "order_id": "ORD-2024-1842",
  "old_status": "PRICE_CALCULATED",
  "new_status": "MANUFACTURING_APPROVED",
  "actor_id": "SEL-007",
  "actor_type": "seller",
  "message": "order status changed to MANUFACTURING_APPROVED"
}
```

### Компоненты и связи

- **Promtail** читает stdout Shop API, CRM API, MES API → отправляет в Loki по HTTP push API
- **Loki** хранит логи, индексирует только метки (service, env, level, order_id — для высокой кардинальности лучше через grep, не метку)
- **Grafana** читает из Loki через LogQL, корреляция с трейсами через `{trace_id="..."}` в Jaeger

### Политика безопасности

**Что не должно попадать в логи:**
- ФИО, адреса, телефоны, email клиентов — только `user_id`
- Платёжные данные (номера карт, CVV, токены) — никогда
- Содержимое 3D-файлов — только `file_id` и `file_size_bytes`
- Пароли, API-ключи, JWT-токены — только факт использования (например, `api_key_id`)

**Обеспечение:** code review на предмет логирования чувствительных данных; в CI можно добавить статический анализатор (например, semgrep с правилами на шаблоны PII в log-вызовах).

**Доступ к логам в Grafana:**
- Роль «Support» — чтение логов всех сервисов в prod, но без возможности смотреть DEBUG-логи
- Роль «Engineering» — чтение всех логов, включая DEBUG в dev/release
- Роль «DevOps» — полный доступ, включая настройку retention и алертов
- Роль «Management» — только агрегированные дашборды (количество заказов, ошибки), не raw logs

**Loki не exposed externally**: работает внутри VPC, Grafana за NGINX reverse proxy с SSO-аутентификацией.

**Audit log**: в Grafana включить audit logging — кто и когда запрашивал логи. Это важно при работе с персональными данными (даже если мы стараемся их не логировать, иногда user_id этого достаточно для идентификации).

### Политика хранения

| Тип логов | Срок хранения | Обоснование |
|-----------|--------------|-------------|
| INFO-логи prod | 30 дней | Достаточно для разбора инцидентов; большинство жалоб поступают в течение нескольких дней |
| WARN-логи prod | 60 дней | Тренды нежелательных ситуаций полезно смотреть в более широком окне |
| ERROR-логи prod | 90 дней | Периодические ошибки могут всплывать циклически; 3 месяца позволяют видеть паттерны |
| DEBUG-логи dev/release | 7 дней | Технический отладочный материал, нужен только «здесь и сейчас» |
| Audit-логи | 1 год | Требование безопасности/compliance; кто и когда смотрел данные |

**Отдельный Loki tenant (или stream) на каждый сервис**: `{service="shop-api"}`, `{service="crm-api"}`, `{service="mes-api"}`. Это позволяет:
1. Устанавливать разные retention policies на разные сервисы
2. Выдавать более гранулярные права (например, партнёры не должны видеть внутренние логи)
3. Считать стоимость хранения по сервису

**Объём хранения (оценка):** при текущем росте (+100 заказов/месяц) и среднем объёме 50 событий на заказ → ~5000 событий/месяц. При среднем размере JSON-лога 500 байт → ~2.5 МБ/месяц на бизнес-события. Технические (HTTP access) добавят ещё ~10x. С Loki-сжатием итого ~3–5 МБ/месяц. Это ничтожно мало даже без специальной заботы о дисковом пространстве.

### От сбора логов к аналитике и алертингу

#### Алертинг на аномалии

Все алерты реализуются через Grafana Alerting → Alertmanager → Telegram (та же цепочка, что и для метрик из Task 2).

| Правило | LogQL-запрос | Threshold | Severity |
|---------|-------------|-----------|----------|
| Всплеск ошибок в MES API | `rate({service="mes-api", level="ERROR"}[5m])` | > 5/мин | critical |
| Всплеск ошибок в CRM API | `rate({service="crm-api", level="ERROR"}[5m])` | > 3/мин | critical |
| Провал расчёта стоимости | `count_over_time({service="mes-api"} \|= "calculate-price" \|= "ERROR" [5m])` | > 1 | warning |
| Потеря соединения с RabbitMQ | `{service=~"crm-api\|mes-api"} \|= "RabbitMQ" \|= "connection"` | любое ERROR за 1 мин | critical |
| Неожиданно долгий расчёт | `{service="mes-api", event="price_calculation.completed"} \| json \| duration_ms > 1800000` | > 0 за 1 мин | warning |

#### Обнаружение аномалий (anomaly detection)

**DDoS / flood через API:** Подозрительный рост запросов от одного `partner_id` виден сразу в логах. Реализуем два уровня:
- Статический алерт: если RPS от одного `partner_id` превысил лимит за 1 минуту (например, >100 req/min) → WARN-лог уже пишется в сервисе, Grafana на нём строит алерт.
- Динамический анализ (вручную, пока нет ML): Grafana позволяет посмотреть топ `partner_id` по количеству запросов за последний час. DevOps может запускать этот дашборд при подозрении на flood.

**Аномальный рост создания заказов:**
```logql
sum by (order_source) (rate({service="shop-api", event="order.created"} [1m]))
```
Если за последние 5 минут значение более чем в 3 раза выше среднего за предыдущий час — алерт. В Grafana это реализуется через функцию `avg_over_time` с временным окном для baseline.

**Паттерн «заказ завис»:** Можно реализовать с помощью лог-метрики: добавить в CRM API лог-событие каждый раз, когда заказ находится в одном статусе более X часов (по scheduled job). Grafana будет считать количество таких событий.

**«Silent errors»** — ситуация, когда ошибки есть, но они не логируются явно (например, проглоченные исключения). Их косвенно обнаруживаем через расхождение: количество событий `order.status.changed → PRICE_CALCULATED` значительно меньше числа событий `order.submitted`. Разрыв в метриках = потенциально потерянные заказы.

## Бонус: Критерии выбора технологии

### Критерии

| Критерий | Grafana Loki | ELK Stack (Elastic) | OpenSearch | Splunk |
|----------|-------------|---------------------|------------|--------|
| **1. Лицензия** | AGPLv3 (бесплатно) / Grafana Enterprise | Elastic License 2.0 — OSS-функции бесплатно, расширенные (RBAC, алерты) — платно | Apache 2.0 — полностью свободный | Проприетарная — очень дорого |
| **2. Требования к ресурсам** | Низкие: не индексирует содержимое, только метки. 1 CPU / 1 GB RAM для старта | Высокие: инвертированный индекс на всё содержимое. 4+ CPU / 8+ GB RAM | Аналогично ELK. 4+ CPU / 8+ GB RAM | Зависит от инфраструктуры; SaaS-вариант снимает вопрос, но стоит дорого |
| **3. Возможности поиска** | LogQL — label-based + grep по содержимому. Достаточно для большинства задач. Полнотекстовый поиск медленнее ES | Мощный полнотекстовый поиск, агрегации, KQL. Лучший в классе | Аналогично ELK. PPL и SQL-запросы дополнительно | Отличный поиск + SPL — мощный язык аналитики. Лучший для сложных корреляций |
| **4. Интеграция с текущим стеком (Grafana)** | Нативная: Loki — первоклассный datasource в Grafana, связь логов с трейсами и метриками из коробки | Через плагин (не нативно). Требует отдельной настройки | Через плагин. Аналогично ELK | Через плагин или отдельный UI. Хуже интеграция |
| **5. Операционная сложность** | Низкая: простой деплой, минимальная настройка. Один DevOps справится | Высокая: index management, шарды, репликация, ILM-политики, heap tuning JVM | Средняя: чуть проще ELK (без Elastic-специфики), но те же задачи по индексам | Низкая для SaaS. Высокая для on-premise |
| **6. Корреляция с трейсами** | Встроенная в Grafana: из лога по `trace_id` — прямо в Jaeger/Tempo | Требует ручной настройки ссылок | Аналогично ELK | Требует отдельной интеграции |
| **7. Алертинг по логам** | Нативный в Grafana (уже используем). Алерты по LogQL-запросам | Kibana Watcher / Kibana Alerting — мощный, но сложнее в настройке | OpenSearch Alerting — достаточно функциональный | Встроенный, мощный |
| **8. Наличие managed-сервиса в Yandex Cloud** | Нет managed, только self-hosted на EC2 | Нет managed | **Да** — Managed Service for OpenSearch в Yandex Cloud. Backup, scaling, patching — автоматически | Нет |
| **9. Масштабируемость** | Горизонтальная (distributed mode). Для текущего объёма (несколько МБ/месяц) — single node достаточно годами | Горизонтальная, но управление кластером требует опыта | Аналогично ES | Хорошая, но стоимость растёт линейно |
| **10. Стоимость хранения** | Минимальная: нет индексов на контент, хранит только сжатые чанки + label index. ~10x дешевле ES | Высокая: полный инвертированный индекс = большой footprint | Аналогично ES | Лицензирование по объёму данных — растёт с ростом системы |

### Итоговый выбор: Grafana Loki

**Почему Loki, а не OpenSearch:**
- Команда уже развернула Grafana (Task 2/3). Добавить Loki — это буквально один дополнительный сервис и один datasource.
- Единый DevOps-инженер не потянет операционное обслуживание кластера Elasticsearch/OpenSearch параллельно со всем остальным.
- Объём логов «Александрита» при текущем росте — единицы МБ/месяц. Мощь Elasticsearch здесь избыточна.
- Корреляция логов с трейсами из Jaeger работает в Grafana из коробки — это ключевое преимущество при расследовании потерянных заказов.

**Когда стоит пересмотреть в сторону OpenSearch/ELK:**
- Если объём логов вырастет настолько, что LogQL + grep перестанет справляться с latency поиска (>100 ГБ/день)
- Если появится потребность в сложных аналитических запросах по тексту логов (сейчас всё нужное уже в структурированных JSON-полях)
- Если бизнес-аналитики захотят строить сложные dashboard с агрегациями по произвольным полям в реальном времени

При таком сценарии Yandex Cloud Managed OpenSearch — оптимальный вариант: снимает операционную нагрузку с единственного DevOps-инженера.
