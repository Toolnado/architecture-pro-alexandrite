# Выбор и настройка мониторинга в системе

## Мотивация

Сейчас единственный источник информации о состоянии системы — жалобы пользователей. Клиенты звонят менеджерам, менеджеры пишут в разработку, разработка начинает расследование постфактум. К моменту, когда проблема обнаружена, она уже нанесла ущерб: потерянные контракты, просроченные заказы, недовольные клиенты.

Яндекс Метрика фиксирует поведение пользователей на сайте, но не видит ничего за пределами браузера. Она не знает, что RabbitMQ забит задачами расчёта стоимости, что MES не успевает обработать очередь, что база данных работает на пределе по соединениям. API-пользователи вообще не попадают в Метрику — их заказы приходят напрямую в MES.

Мониторинг нужен, чтобы:

**Для бизнеса:**
- Перейти от реактивного режима ("нам пожаловались — мы чиним") к проактивному ("мы видим деградацию — устраняем до того, как клиент заметил").
- Иметь данные для разговора с партнёрами: если они утверждают, что заказ не был обработан, мы можем показать метрики и проследить путь заказа.
- Обоснованно принимать решения о масштабировании: не "кажется, нам нужно ещё серверов", а "CPU MES API держится выше 85% последние две недели при текущем RPS — нужен дополнительный инстанс".

**Для команды:**
- Сократить время диагностики с часов до минут. Вместо "давайте посмотрим логи" — сразу видно, какой компонент деградирует.
- Получать алерты на дежурство, а не из Telegram от клиентов в три ночи.
- Обоснованно оценивать, помогли ли внесённые изменения.

Без мониторинга мы продолжаем лечить симптомы, не понимая причин. Это не технический вопрос — это вопрос того, насколько управляемо ведётся бизнес.

## Выбор подхода к мониторингу

Для разных частей системы используем разные подходы, потому что природа компонентов различается.

### API-сервисы (Shop API, CRM API, MES API) — RED

Shop API, CRM API и MES API — это сервисы, ориентированные на обработку запросов. Для них важно понимать три вещи: сколько запросов приходит, сколько из них падает с ошибкой и как быстро они обрабатываются. Это классический RED (Rate, Errors, Duration).

- **Rate** — количество запросов в секунду. Показывает текущую нагрузку и помогает замечать аномальные всплески (например, flood от партнёров через API).
- **Errors** — доля запросов с ошибкой (HTTP 5xx). Прямой индикатор того, что сервис не справляется или сломан.
- **Duration** — время ответа (latency). Деградация latency часто предшествует росту ошибок — это ранний сигнал.

### Инфраструктура (EC2-инстансы, БД, RabbitMQ) — USE

Серверы, базы данных и брокер сообщений — это ресурсы. Для них важно понимать, насколько они загружены, не подходят ли к пределу и нет ли ошибок на уровне ресурса. Это USE (Utilization, Saturation, Errors).

- **Utilization** — CPU, память, дисковое пространство. Показывает, сколько ресурса используется.
- **Saturation** — очередь сообщений RabbitMQ, количество соединений к БД, concurrent connections. Показывает, не забит ли ресурс до предела.
- **Errors** — сообщения в dead-letter-exchange, ошибки на уровне БД.

### Бизнес-метрики — отдельный слой

Помимо технических метрик, добавляем бизнес-ориентированные: количество заказов по статусам, время нахождения заказа в статусе, время расчёта стоимости. Эти метрики позволяют напрямую видеть состояние бизнес-процессов, а не угадывать их через технические показатели.

## Метрики

### RabbitMQ

#### ✅ Number of dead-letter-exchange letters in RabbitMQ

Сообщения попали в DLX — это значит, что consumer не смог их обработать (превышено число повторных попыток, сообщение отклонено или истёк TTL). Каждое сообщение в DLX — это потенциально потерянный заказ или пропущенное событие смены статуса. Это один из самых важных алертов в системе.

**Ярлыки:** `queue_name` — чтобы понимать, в какой конкретно очереди возникают проблемы (расчёт стоимости, статусные события, уведомления).

#### ✅ Number of messages in flight in RabbitMQ

Количество сообщений, которые уже доставлены consumers, но ещё не подтверждены (unacked). Высокое значение означает, что consumers получают сообщения, но не успевают их обрабатывать — например, расчёт стоимости занимает 30 минут, и за это время накапливаются новые сообщения. Это сигнал перегруженности очереди.

**Ярлыки:** `queue_name`, `vhost`.

#### ➕ Queue depth (messages ready) — дополнительная метрика

Количество сообщений, ожидающих доставки (не в списке, но критически важна). Отличается от in-flight: это сообщения, которые ещё не взяты consumers. Рост глубины очереди — ранний сигнал, что система не справляется с потоком.

**Ярлыки:** `queue_name`.

#### ➕ Consumer count per queue — дополнительная метрика

Количество активных consumers на очереди. Если consumers отвалились (краш, перезапуск), очередь будет расти, но никто этого не заметит, пока не придут жалобы. Этот алерт закрывает этот сценарий.

**Ярлыки:** `queue_name`.

### Shop API

#### ✅ Number of requests (RPS) for internet shop API

Базовая RED-метрика трафика. Позволяет видеть текущую нагрузку, замечать аномальные всплески (DDoS, ошибки клиентского кода) и понимать, при каком RPS начинается деградация.

**Ярлыки:** нет (агрегированная метрика по сервису).

#### ✅ Number of requests (RPS) per user for internet shop API

Позволяет обнаруживать аномальное поведение отдельных пользователей: бот-трафик, сломанный скрипт, попытки перебора. Также пригодится для будущего rate limiting'а — сначала нужно измерить, потом ограничивать.

**Ярлыки:** `user_id` или `ip` — зависит от того, аутентифицированы ли запросы.

#### ✅ Response time (latency) for shop API

RED-метрика Duration. Важно отслеживать не только среднее, но и перцентили (p50, p95, p99). Среднее latency может быть нормальным, пока 5% запросов висят по 10 секунд — перцентили это покажут.

**Ярлыки:** `endpoint`, `method` — чтобы понимать, какой конкретно эндпоинт тормозит.

#### ✅ Number of HTTP 500 for shop API

RED-метрика Errors. Прямой индикатор сбоев в сервисе. Важно отслеживать как абсолютное значение (сколько ошибок за период), так и долю от общего числа запросов (error rate).

**Ярлыки:** `endpoint` — чтобы быстро локализовать проблемный путь.

#### ⚠️ Number of HTTP 200 for shop API

Метрика нужна, но в изоляции малоинформативна. Рекомендую заменить отдельные метрики по кодам на единую метрику `http_requests_total` с ярлыком `status_code` (или группой: `2xx`, `4xx`, `5xx`). Это удобнее для анализа: можно строить любые срезы — error rate, success rate, доля 4xx относительно 5xx.

**Ярлыки:** `status_code`, `endpoint`, `method`.

#### ✅ CPU % for shop API

USE-метрика Utilization. Показывает, насколько загружен процессор. При росте нагрузки CPU растёт раньше, чем начнут падать запросы — это позволяет масштабировать заблаговременно.

**Ярлыки:** `instance` — на случай, если инстансов станет несколько.

#### ✅ Memory Utilisation for shop API

USE-метрика Utilization. Spring Boot-приложения могут иметь утечки памяти; рост потребления памяти со временем — ранний сигнал проблемы. Также важно для настройки JVM heap.

**Ярлыки:** `instance`.

#### ✅ Number of simultaneous sessions for shop API

USE-метрика Saturation. Показывает, сколько соединений одновременно обрабатывается. Если это значение близко к максимуму thread pool или connection pool — новые запросы начнут ждать или получать ошибки.

**Ярлыки:** `instance`.

#### ❌ Kb transferred (received/sent) for shop API

Полезна для оценки сетевого трафика и capacity planning, но в текущей ситуации не приоритетна — узкое место не в пропускной способности сети. Можно добавить позже.

### CRM API

#### ✅ Number of requests (RPS) for CRM API

CRM используется менеджерами по продажам — нагрузка предсказуемая и рабочая. Метрика нужна для baseline и обнаружения аномалий (например, если интеграция с MES начнёт слать лишние запросы).

**Ярлыки:** нет.

#### ❌ Number of requests (RPS) per user for CRM API

CRM — внутренний инструмент с ограниченным числом пользователей. Аномальный RPS от конкретного пользователя здесь маловероятен. Не приоритетно.

#### ✅ Response time (latency) for CRM API

Менеджеры жалуются на скорость работы — baseline latency нужен, чтобы измерить улучшения после оптимизаций.

**Ярлыки:** `endpoint`, `method`.

#### ✅ Number of HTTP 500 for CRM API

Ошибки в CRM — это сбои в работе менеджеров, нужно знать о них немедленно.

**Ярлыки:** `endpoint`.

#### ✅ CPU % и Memory Utilisation for CRM API

Аналогично Shop API — нужны для контроля утилизации ресурсов.

**Ярлыки:** `instance`.

#### ✅ Number of simultaneous sessions for CRM API

**Ярлыки:** `instance`.

#### ❌ Kb transferred for CRM API

Не приоритетно — CRM оперирует небольшими JSON-объектами.

### MES API

#### ✅ Number of requests (RPS) for MES API

MES API — это публичный эндпоинт для расчёта стоимости, которым пользуются внешние партнёры. Именно здесь нужно замечать flood от партнёров до того, как он положит систему.

**Ярлыки:** `endpoint`.

#### ✅ Number of requests (RPS) per user for MES API

Это ключевая метрика для внешнего API. Позволяет видеть, кто из партнёров перегружает систему (намеренно или случайно), и принимать решения о rate limiting'е. Без неё невозможно обосновать введение ограничений.

**Ярлыки:** `api_key` или `partner_id`.

#### ✅ Response time (latency) for MES API

Особенно важна для эндпоинта расчёта стоимости — время ответа может достигать 30 минут. Нужно отслеживать перцентили, чтобы понимать распределение времени обработки по сложности моделей.

**Ярлыки:** `endpoint`, `method`.

#### ✅ Number of HTTP 500 for MES API

Ошибки в публичном API напрямую влияют на партнёров и репутацию сервиса.

**Ярлыки:** `endpoint`, `partner_id`.

#### ✅ CPU % и Memory Utilisation for MES API

MES делает вычислительно тяжёлые операции (расчёт стоимости по 3D-модели). CPU-утилизация здесь особенно важна.

**Ярлыки:** `instance`.

#### ✅ Number of simultaneous sessions for MES API

Если все потоки заняты долгими расчётами, новые запросы будут ждать. Это сигнал для масштабирования воркеров.

**Ярлыки:** `instance`.

#### ✅ Kb transferred (received) for MES API

В отличие от других API, MES получает 3D-файлы или ссылки на них. Объём входящих данных здесь значителен и влияет на пропускную способность и latency. Стоит отслеживать.

**Ярлыки:** `endpoint`.

### Базы данных

#### ✅ Memory Utilisation for shop db instance и MES db instance

БД активно использует память для кэширования. Если память заканчивается, запросы начинают ходить на диск — latency вырастает в разы. Критически важна для MES db, которая сейчас является узким местом.

**Ярлыки:** `db_name`, `instance`.

#### ✅ Number of connections for shop db instance и MES db instance

USE-метрика Saturation. При приближении к `max_connections` новые подключения отклоняются с ошибкой. Нужно алертить при превышении 80% от лимита, чтобы успеть среагировать до деградации.

**Ярлыки:** `db_name`.

#### ✅ Size of shop db instance и MES db instance

Capacity planning. Disk full = полный отказ БД. Нужен алерт заблаговременно — диск нельзя расширить мгновенно.

**Ярлыки:** `db_name`.

#### ➕ Query latency (p95, p99) — дополнительная метрика

Медленные запросы — прямая причина проблем с дашбордом MES. Нужно знать, какие запросы тормозят. Yandex Cloud для Managed PostgreSQL предоставляет `pg_stat_statements` — можно выгружать топ медленных запросов.

**Ярлыки:** `query_hash` или `query_type`.

#### ➕ Slow query count — дополнительная метрика

Количество запросов, выполнявшихся дольше порогового значения (например, 1 секунды). Позволяет быстро увидеть регрессию после деплоя — если slow query count вырос, значит что-то сломалось на уровне запросов.

**Ярлыки:** `db_name`, `threshold`.

---

### S3 / File Storage

#### ✅ Size of S3 storage

Capacity planning для хранилища 3D-файлов. При росте числа заказов хранилище растёт линейно. Нужен алерт при превышении планового лимита для принятия решений об архивировании или увеличении квоты.

**Ярлыки:** `bucket_name`.

### Бизнес-метрики (дополнительный слой)

Эти метрики не попали в исходный список, но являются самыми важными для мониторинга бизнес-здоровья системы.

#### ➕ Number of orders by status

Количество заказов, находящихся в каждом статусе в данный момент. Позволяет видеть "пробки": если сотни заказов зависли в `SUBMITTED`, значит расчёт стоимости не работает; если много заказов в `PRICE_CALCULATED` но не в `MANUFACTURING_APPROVED`, значит проблема в CRM или очереди.

**Ярлыки:** `status`, `order_source` (b2c / b2b).

#### ➕ Order age by status (time in status)

Сколько времени в среднем заказ проводит в каждом статусе. Если `time in SUBMITTED → PRICE_CALCULATED` растёт — MES перегружен. Это метрика, которая напрямую отвечает на вопрос "почему клиенты жалуются на задержки".

**Ярлыки:** `status`, `order_source`.

#### ➕ Price calculation duration

Время, которое MES тратит на расчёт стоимости конкретного заказа. Позволяет видеть распределение: медиана — 2–3 минуты, хвост — до 30 минут. Полезно для планирования capacity и SLA с партнёрами.

**Ярлыки:** `order_source`, `model_complexity` (если доступно).

## План действий

### 1. Инфраструктура для сбора и хранения метрик

- Создать инстанс **VictoriaMetrics** (или использовать Yandex Cloud Monitoring) как time-series базу данных. VictoriaMetrics хорошо интегрируется с Prometheus-совместимыми источниками и имеет меньший footprint, чем Prometheus при больших объёмах данных.
- Развернуть **Grafana** для визуализации (managed instance или EC2). Настроить datasource на VictoriaMetrics.
- Настроить **Alertmanager** (или встроенные алерты Grafana) с доставкой уведомлений в Telegram/Slack дежурному инженеру.

### 2. Инструментирование приложений

- **Shop API и CRM API (Java Spring Boot):** добавить зависимость `micrometer-registry-prometheus` в `pom.xml`. Spring Boot Actuator автоматически экспортирует JVM-метрики, метрики HTTP-запросов, thread pool. Дополнительно добавить кастомные бизнес-метрики через `MeterRegistry`.
- **MES API (C#):** добавить NuGet-пакет `prometheus-net.AspNetCore`. Он автоматически собирает HTTP-метрики, метрики CLR (память, GC, потоки). Добавить кастомный `Histogram` для времени расчёта стоимости.
- Для всех сервисов: добавить эндпоинт `/metrics`, закрыть его от внешнего доступа (только internal network).

### 3. RabbitMQ

- Включить **Prometheus plugin** (`rabbitmq-plugins enable rabbitmq_prometheus`). RabbitMQ начнёт отдавать метрики на `/metrics` — queue depth, messages in flight, consumer count, DLX count, и другие.
- Настроить scrape в VictoriaMetrics/Prometheus.

### 4. Базы данных

- Для **Managed PostgreSQL** в Yandex Cloud: метрики CPU, память, connections, disk usage доступны через Yandex Cloud Monitoring автоматически. Настроить их экспорт в Grafana через Yandex datasource.
- Включить **pg_stat_statements** для мониторинга медленных запросов. Настроить экспорт через `postgres_exporter`.

### 5. S3 / File Storage

- Настроить метрики через Yandex Cloud Object Storage Monitoring: объём данных, количество объектов, количество запросов. Доступны в Yandex Cloud Monitoring из коробки.

### 6. Бизнес-метрики

- В Shop API и CRM API добавить инструментирование: при каждой смене статуса заказа инкрементировать счётчик `orders_by_status` с соответствующим ярлыком.
- Добавить gauge `order_age_seconds` — обновляется по расписанию (раз в минуту), агрегирует по статусам.
- В MES API добавить `Histogram` для времени расчёта стоимости.

### 7. Дашборды и алерты

- Создать дашборды в Grafana: отдельный для каждого сервиса (RED-дашборд) и общий операционный дашборд (бизнес-метрики + очереди + БД).
- Настроить алерты (минимальный набор для старта):
  - DLX count > 0 в течение 5 минут
  - Queue depth > 100 для очереди статусных событий
  - HTTP 5xx rate > 1% в течение 5 минут для любого API
  - CPU > 80% в течение 10 минут
  - DB connections > 80% от max_connections
  - Disk usage > 75%

### 8. Деплой и настройка в окружениях

- Начать с **prod**: мониторинг нужен там, где проблемы. Dev и release можно подключить позже.
- Весь стек мониторинга описать как Infrastructure as Code (Terraform или Ansible) для воспроизводимости.

## Показатели насыщенности

Насыщенность (Saturation) — это мера того, насколько ресурс близок к своему пределу. В отличие от Utilization (сколько ресурса используется), Saturation показывает, есть ли очередь ожидания: работа не выполняется потому, что ресурс занят.

### 1. RabbitMQ — Queue Depth (messages ready)

**Пороговое значение:**
- Очередь статусных событий: > 50 сообщений — warning, > 200 — critical.
- Очередь расчёта стоимости: > 20 заказов — warning, > 100 — critical.

**Почему именно эти значения:** статусные события должны обрабатываться быстро (секунды), поэтому даже небольшое накопление — это сигнал. Расчёт стоимости может занимать до 30 минут, поэтому небольшая очередь нормальна, но при накоплении более 100 заказов ожидание последнего в очереди составит несколько часов.

**Действия при превышении:**
- Warning: дежурный инженер проверяет состояние consumers (не упали ли), смотрит на latency расчёта.
- Critical: немедленный алерт, эскалация к тимлиду. Если consumers живы — добавить воркеры расчёта (вручную, до настройки автоскейлинга). Завести тикет с приоритетом P1.

### 2. Базы данных — Number of Connections

**Пороговое значение:**
- 70% от `max_connections` — warning.
- 85% — critical.

**Почему:** при 100% новые подключения отклоняются немедленно с ошибкой. Нужен буфер: 15–30% запаса даёт время среагировать до того, как пользователи получат ошибки. По умолчанию в PostgreSQL `max_connections = 100` (для Managed PostgreSQL Yandex Cloud — настраивается). При 70 активных соединениях уже стоит разбираться, нет ли connection leak или пула, который не возвращает соединения.

**Действия при превышении:**
- Warning: проверить `pg_stat_activity`, найти долгоживущие или idle соединения. Проверить настройки connection pool в приложении.
- Critical: немедленный алерт. Если connection leak — перезапуск сервиса (с предупреждением). Увеличить `max_connections` через Yandex Cloud Console (требует перезапуска БД, планировать заранее). Завести тикет на проверку пула соединений.

### 3. EC2 / CPU Utilization

**Пороговое значение:**
- > 80% в течение 10 минут — warning.
- > 90% в течение 5 минут — critical.

**Почему:** при CPU > 90% приложение начинает пропускать дедлайны планировщика, растёт latency запросов. 80% — точка, при которой пиковые нагрузки могут перевалить за 100% и вызвать деградацию. Окно 10 минут исключает ложные срабатывания от коротких пиков (например, GC или разогрев JIT).

**Действия при превышении:**
- Warning: проверить, не началась ли нетипичная нагрузка (spike в трафике, зависший процесс). Если нагрузка штатная и растущая — спланировать вертикальное масштабирование (upgrade EC2 type).
- Critical: немедленно проверить запущенные процессы. Если это MES во время расчёта — рассмотреть добавление инстанса вручную. Завести тикет на настройку горизонтального масштабирования.

### 4. Memory Utilization

**Пороговое значение:**
- Приложения (JVM/CLR): > 85% heap utilization в течение 15 минут — warning; > 95% — critical.
- БД: > 90% — warning; > 95% — critical.

**Почему:** JVM при заполненном heap начинает агрессивный GC, что вызывает stop-the-world паузы и всплески latency. При 100% — OOM и падение процесса. БД использует память для buffer cache: при нехватке запросы идут на диск, latency растёт на порядок.

**Действия при превышении:**
- Warning для приложения: снять heap dump, проанализировать утечки. Если утечки нет — запланировать увеличение heap или upgrade инстанса.
- Critical: немедленный алерт, эскалация. Если приложение не отвечает — перезапуск (с понятием о потере in-flight запросов).
- Для БД: увеличить объём RAM инстанса через Yandex Cloud (downtime ~5 минут), написать в Yandex Cloud Support.

### 5. RabbitMQ — Dead Letter Exchange Count

**Пороговое значение:** > 0 сообщений в DLX в течение 5 минут — critical (нет уровня warning).

**Почему:** сообщение в DLX — это безвозвратно потерянный заказ или пропущенное событие. Это не "возможная проблема", это уже произошедшая потеря данных. Нет смысла делать warning — нужно реагировать сразу.

**Действия:**
- Немедленный алерт дежурному и тимлиду.
- Вручную разобрать сообщения в DLX: понять, что не удалось обработать и почему.
- Переиграть сообщения (replay) из DLX после устранения причины.
- Завести тикет P0/P1 на причину отказа consumer.
- Если это системная проблема — эскалировать немедленно, не ждать утра.
